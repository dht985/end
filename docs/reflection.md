# 个人反思

## 一、最大亮点

**"单一数据源 + 统一封装"驱动的全站一致性**。全站五页共享一份 navy-data.json，筛选下拉选项、时间线标签按钮均由数据动态生成（新增一条装备记录，装备页选项、计数、图表构成自动同步，无需改界面代码）；`loadNavyData` + `renderState` 把"加载/空/错"三态收敛为两个公共函数，七处内容区提示语言完全一致。这套机制让"数据与图表一致性核验"（charts.md 第二节）可以逐项对账——发现并修正了 2 处真实的数据口径问题，这正是统一数据源架构带来的可验证性。

次亮点：全资源本地化的**完全离线可用**（断网后含三维场景在内全部功能照常），以及基于双服务器对照实验的加载优化（equipment 页 DCL -75%，且用数据否定了"无脑 defer"的方案，见 performance.md）。

## 二、最大不足

**交互深度停留在"筛选-展示"层面，缺少写操作与状态保持**：装备/历程只有查询与过滤，没有"添加/修改"类管理能力；筛选条件不写入 URL，刷新或分享链接后筛选状态丢失；三维场景只有环视与漫游，缺少点击拾取这类"由用户好奇心驱动"的交互。

## 三、局限性与改进计划（若再有一周）

| 局限 | 改进方向（一周内） |
|---|---|
| 无管理能力，数据更新需手改 JSON | 增加"装备收藏/备注"模块：`localStorage` 实现添加、修改、删除，与 JSON 基础数据合并渲染，补充表单校验（必填/排水量格式），管理操作也走三态提示 |
| 筛选状态不持久、不可分享 | 筛选条件同步到 URL hash（如 `#type=carrier&era=2010s&kw=16`），加载时反解析还原，支持直接分享筛选结果链接 |
| 三维场景无点击交互，信息密度低 | 为五组舰船绑定 A-Frame cursor 点击事件，点击弹出舷号/排水量信息面板（数据取自同一 JSON），并实现相机飞向该舰的聚焦动画 |
| 图表各自独立，无联动 | 建立简单状态总线：点击饼图某舰种扇区 → 柱状图高亮对应年代、下方过滤出该舰种装备列表（ECharts 事件 + 状态变量驱动） |
| 性能测量依赖手工脚本 | 把 Playwright 测量脚本固化为 npm script + 阈值告警（DCL 超过基线 30% 即报错），防止后续改动悄悄劣化加载性能 |
| 移动端三维体验未专门优化 | 触屏 look-controls 已由 A-Frame 支持，但 WASD 对手机无意义，拟增加虚拟摇杆或"自动巡航"按钮 |

## 现场解释备忘（可能的追问）

- 为什么 A-Frame 页不用 defer？→ 实测 DCL +22ms，场景页正文为空、无内容可先渲染，defer 无收益（见 performance.md 与 showcase.html 源码注释）；
- 非法输入为什么不怕 XSS？→ 用户输入仅作为 `indexOf` 的匹配串参与过滤，不作为 HTML 片段插入内容区；
- 数据从哪来、可信吗？→ 公开资料整理，JSON `meta.source` 声明来源且注明"仅作学习展示"。
